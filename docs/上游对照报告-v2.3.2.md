# 上游对照报告：yuan71058/FastGithub v2.3.2 vs 本仓库 v2.6.10

> 对照时间：2026-10-30。方法：GitHub API 拉取上游 master 全量文件树（170 文件），
> 与本地 223 个代码文件做 git blob SHA 全量比对（共同文件 162，内容一致 121，有差异 41），
> 再逐文件审阅 41 份 unified diff 与上游独有的 7 个文件。
> 上游 v2.3.2 发布于 2026-10-06（与本仓库 v2.6.9 同日）。

## 一、总体格局

两个仓库同源但已大幅分叉，**方向不同**：

- 本仓库（v2.6.x）：深度自研**解析/建连可靠性层**——IpHealthTracker 健康度闭环、
  DoH 多端点熔断+半开+递增冷却、按域 ConnectTimeout/Timeout 分级、建连预算切片、
  hosts 源单飞合流+失败退避+无效IP过滤、解析兜底种子表、探测缓存保留策略、
  13+ 条 --SelfTest 自检断言、/diagnostics /connectivity /shutdown 诊断端点、
  拦截器降级存活（正向代理回退）、UI 确认退出+孤儿进程防护。
- 上游（v2.3.2）：解析层保持简单版（connectTimeout 5s 硬编码、无健康度跟踪、
  拦截器失败直接停机），把精力放在**产品化功能**——在线 hosts 源 JSON 化、
  域名测速并发化、托盘「更新IP」全链路反馈、CI/CD 自动化。

结论：可靠性层无需回流，上游有 4 处独立改进值得借鉴（其中 1 处对应本仓库一个真实 bug）。

## 二、建议借鉴（按价值排序）

### A1. CI/CD 工作流——高价值；且本仓库已有，但 26 次运行全部失败

**【v2.6.11 勘误】** 初版报告称"本仓库没有 workflows"——错误：当时的文件树扫描
排除了点前缀目录，漏掉了 `.github/`。本仓库自 v2.4.0 起就有完整的 build.yml +
release.yml（net10.0、仅 win-x64、无裁剪、发布前校验关键文件、剔除 cacert 私钥），
设计上已解决"被墙的 push/上传"问题。

**但 Actions 历史上 26 次运行全部失败（2026-10-03 ~ 10-07），之后未再成功触发过。**
v2.6.11 已定位唯一根因：仓库 `NuGet.config` 只配华为云镜像，
该镜像在 GitHub runner 上 nupkg 下载损坏（"End of Central Directory record could
not be found"），restore 与 UI publish 全部因此挂掉。
修复：CI 内临时覆盖为 nuget.org（不影响本机 restore），并顺手：
- build.yml 增加 `--SelfTest` 冒烟步骤（先 continue-on-error 观察几轮）与 workflow_dispatch；
- release.yml 发布说明优先读取仓库内 `release-notes/<tag>.md`（单一事实来源）。

后续待验证（首次 CI 成功后确认）：
- UI 项目 net45+Costura 在 runner 上的 targeting pack 是否齐全；
- `--SelfTest` 在 runner 上可稳定运行后转为阻塞步骤。

### A2. `/refresh-ip` 与请求生命周期解耦——对应本仓库一个真实 bug

上游：`using var cts = new CancellationTokenSource(45s)` 用**独立超时预算**驱动刷新，
不绑定 `context.RequestAborted`；返回 JSON 真实结果（域名数/可用IP数/hosts源状态）。
UI 侧超时 60s，3 秒未完成先给一次"进行中"反馈。

本仓库现状：`await resolver.RefreshHostsAsync(context.RequestAborted)` + UI 超时仅 **10s**。
手动刷新走"清缓存→全量重解析→并发测速"，一旦超过 10s，UI 断开即把刷新拦腰砍断——
且我们的刷新语义是先失效解析缓存，砍断后系统处于**半刷新状态**（缓存已清、新结果未就绪）。
这是真实缺陷，建议照抄上游的解耦模式。

### A3. UI 全局异常兜底

上游实证过的真实故障：日志页右键复制时剪贴板被其它进程占用，`Clipboard.SetText`
抛 COMException → 托盘进程崩溃 → 后端随父进程退出 → 加速静默失效。

```csharp
app.DispatcherUnhandledException += (s, e) => e.Handled = true;
AppDomain.CurrentDomain.UnhandledException += (s, e) => { };
```

本仓库 UI 无任何全局兜底（已 grep 确认），且同样有剪贴板复制功能。两行代码。

### A4. JSON hosts 源解析

上游默认源改为 `https://raw.hellogithub.com/hosts.json`（`[["ip","domain"],...]` 数组），
`Parse` 自动探测格式：`[` 或 `{` 开头走 JSON，否则走原文本 hosts 格式。

本仓库 HostsService **只解析文本格式**（已确认）。若该源格式迁移，hosts 通道静默失效
（我们有"失败保留旧映射"保护，不至于清空，但通道就此报废）。
借鉴时**保留**本仓库已有的 IpAddressFilter 无效IP过滤与单飞合流/退避——上游 JSON 分支没有这些。

### A5.（顺带）日志复制剪贴板重试

`Clipboard.SetText` 重试 3 次、每次间隔 100ms、COMException 吞掉。
与 A3 是同一故障的两半，几行代码，一并修。

## 三、可选（低优先级）

- **主窗口状态栏**：版本号常驻 + IP 更新结果回显（"IP更新完成：N个域名、M个可用IP"）。
  我们当前只弹"已发送IP更新请求"，用户不知道结果。配合 A2 的 JSON 返回一起做才有意义。
  用户偏好"尽量少改 UI"，状态展示非交互改动，可做可不做。
- **备用 DNS 服务器扩充**：上游加 210.2.4.8（CNNIC）、8.8.8.8 并"不可达自动跳过"。
  本仓库 10 月日志实测 TCP:53 明文 DNS 对 223.5.5.5/119.29.29.29 **全被 RST**（ISP 级干扰），
  加服务器大概率同样被 RST；且我们的 DnsClient 已有 10 分钟"假可达"冷却机制。收益预计为零。

## 四、明确不借鉴（本仓库已领先或不适配）

| 上游做法 | 不借鉴原因 |
|---|---|
| 解析层无健康度跟踪、connectTimeout 全局 5s 硬编码 | 本仓库 IpHealthTracker 分级/预算切片/种子表全面领先，有日志实证 |
| 域名测速并发化（Parallel.ForEachAsync, 8路） | 本仓库已用 SemaphoreSlim(8) 实现，且多了缓存回写防 504 争抢 |
| 刷新时清空全部缓存 | 本仓库刻意保留探测缓存防"探测风暴"，只失效解析缓存——有 v2.6.4 实测依据 |
| hosts 源 IP 无过滤直接采用 | 本仓库 IpAddressFilter 过滤环回/内网/污染段，日志曾实证 127.0.0.1 入选事故 |
| 拦截器失败即 StopAsync 停机 | 本仓库已实现降级存活（正向代理 + PAC 指引），上游反而是退步方向 |
| UiApi /ping 端口探测（45678 顺延 10 个） | 本仓库用 --UiHttpPort 显式传参 + GetAvailableTcpPort，比盲探更可靠 |
| dnscrypt bootstrap 9.9.9.9/8.8.8.8 | 本机网络环境用国内 bootstrap（223.5.5.5/119.29.29.29）更合理 |
| net7.0 / PublishTrimmed | 本仓库 net10.0；Trimmed 对 WinDivert/反射场景有裁剪风险 |
