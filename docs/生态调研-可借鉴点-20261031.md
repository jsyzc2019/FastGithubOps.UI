## 二、值得借鉴（按价值排序）

### B1.（本次新发现，生态内无人使用）GitHub 官方 meta API 做候选池扩充

`https://api.github.com/meta` 返回官方 CIDR 段：`web` 41 段、`api` 27 段、`git` 62 段、
`packages`/`pages`/`shared_ingress` 等，且有 SSH 指纹佐证真实性。
**已实测验证**：我们已知的 github.com 真实 IP（20.205.243.166、140.82.121.3/4、
20.26.156.215）全部落在 `web` 段内。

这正好打我们的核心痛点——**v2.6.9 审计确认 github.com 权威 DNS 常态只回 1 条 A 记录，
候选池=1 是单点**。设想：
- 解析 github.com 得 1 个 IP 时 → 从 `web` 段全集（或该 IP 所属段）采样若干候选
  （如每 /24 取一个，限量）→ 走现有 TCP+TLS 实测竞速 + IpHealthTracker 筛选 →
  单 IP 域名的候选池从 1 扩到 N；
- `api.github.com` 本机可达（200 通），meta 数据可缓存数天（官方段变化低频）；
- 纯增量：不动现有 DoH/DNS 链路，作为额外候选源排在 DoH 之后。

风险与对策：段内采样可能命中不可用 IP——但现有实测竞速+健康度天然兜底；
需限制采样数量防止探测风暴（复用 speedSemaphore 限流）。

### B2. hosts 多源冗余（改动小，直接收益）

当前 `FastGithub:HostsUrl` 只支持单源。生态里有三个活跃源可做顺序 failover：
1. `https://raw.hellogithub.com/hosts.json`（现用，JSON）；
2. GitHub520：`https://raw.githubusercontent.com/521xueweihan/GitHub520/main/hosts`（文本）；
3. ineo6/hosts：`https://gitlab.com/ineo6/hosts/-/raw/master/next-hosts`（文本，GitLab 双保险）。

改法：`HostsUrl` → `HostsUrls` 数组，按序尝试（沿用现有单飞合流+失败退避，
单源失败自动下一个），解析层零改动（文本/JSON 已双格式支持）。

### B3.（方向性，动 UI 与信任面，暂缓）镜像回退通道

dev-sidecar 的核心差异点："拦截打不开的网站代理到加速镜像站，多镜像备份，
访问失败/超时自动切换"；gh-proxy 证明 URL 前缀重写（`<mirror>/https://github.com/...`）
对 release/archive/raw 文件下载有效。

对本仓库：可做"**最后兜底通道**"——当某域名所有候选 IP 拉黑且刷新后仍无可用时，
把 release/raw 类请求重写到用户自配的镜像站。注意点：
- 信任面扩大（镜像站可见流量内容），必须用户显式配置、默认关闭；
- 只对幂等 GET（release/archive/raw）启用，clone/push 不碰；
- 与现有健康度闭环的交互要设计好（镜像通道成功不应洗白直连 IP）。
建议等 B1/B2 落地后再评估必要性——直连成功率上来后，镜像通道的边际价值存疑。

## 三、不适用/无需借鉴

| 项目/做法 | 结论 |
|---|---|
| creazyboyone/FastGithub | 停更（2025-08），改动为版本解析修补+云编译，无增量价值 |
| GitHub520/ineo6 的静态 hosts 思路本身 | 无测速无健康度，质量不如我们的竞速链路；只取"多源"这一层（B2） |
| dev-sidecar 的油猴脚本注入/远程配置体系 | Electron 插件架构不匹配本项目，且引入供应链信任面 |
| hubproxy / CF-Workers 系（cmliu、1234567Yang 等） | 服务端自部署形态，与本机透明拦截定位不同；若做 B3 可参考其 URL 规则 |
| Watt Toolkit(Steam++) hosts 模式 | 架构不同（纯 hosts 替换），无机制可借 |
| dev-sidecar 的"Electron 关机事件丢代理"教训 | 我们无此问题（WinDivert + 孤儿进程防护已覆盖），反证现有设计正确 |
