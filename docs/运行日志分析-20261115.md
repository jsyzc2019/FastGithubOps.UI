# 运行日志分析（2026-11-15，v2.6.12 → v2.6.13 升级当天）

> 数据源：`D:\fastgithub-my\logs\log20261115.txt`（实时写入，分析时 16,096 条 / 2.9MB），
> 对照 `log20261031~20261114.txt`。复跑：`python tools/log-analysis/analyze_logs.py "D:\fastgithub-my\logs" 20261115`

## 一、结论先说

「错误比较多」的观感由两件**性质完全不同**的事叠加而来，必须分开处理：

| 类别 | 体量 | 用户是否可感知 | 性质 |
|---|---|---|---|
| 明文 DNS `Refused` 告警 | **7,979 条，占当天日志 50.2%** | 否（DoH 已兜住） | 日志噪声 + 无效重试 |
| 真实失败（502/504） | **179 次 / 3,025 请求 = 5.92%** | 是 | **77% 集中在两次重启后的 15 分钟内** |

把区间拆开看，稳态其实很好：

| 区间 | 请求 | 502/504 | 失败率 |
|---|---|---|---|
| 00:00–14:58 v2.6.12 稳态（含整夜空闲） | 10 | 1 | — |
| 14:59–15:13 **重启窗口** | 9 | 7 | 77.8% |
| 15:14–16:41 v2.6.12 稳态 | 533 | 1 | **0.19%** |
| 16:42–16:56 **重启窗口** | 271 | 86 | **31.7%** |
| 16:57–18:19 v2.6.12（含 49MB Release 下载占满带宽） | 822 | 27 | 3.28% |
| 18:20–18:34 **重启窗口（v2.6.13）** | 706 | 53 | **7.51%** |
| 18:35–21:38 v2.6.13 稳态 | 672 | 4 | **0.60%** |

→ 所以真正要修的不是「错误率」，而是**启动后那 10 分钟**＋**一件事的降噪**。

## 二、噪声：明文 DNS 在本机是「假可达 + REFUSED」

现象：`DnsClient` 共 8,078 条，其中 7,979 条是
`域名@223.5.5.5:53->Invalid response received with code Refused`，覆盖全部 22 个域名、
两个 fallback DNS，**每域名 ~400 条/天**；0–6 点整机空闲时同样 ~360 条/小时，
与用户请求量无关（对比 11-13 是 1s 测速周期、今天 60s，两边每小时的 Refused 量几乎一致）。

实测（FastGithub 运行中，`analysis/dnstest.py`、`tcp53b.py`）：

| 探测 | 结果 |
|---|---|
| UDP 53 → 223.5.5.5 查 `github.com` | NOERROR，A=127.0.0.1（DnsInterceptor 正常改写） |
| UDP 53 → 223.5.5.5 查 `baidu.com` | NOERROR，A=真实 IP（UDP 通道健康） |
| TCP 53 → 223.5.5.5 / 119.29.29.29 / 8.8.8.8 | 握手 0.01–0.03s 成功，之后查询 15s 无响应 |
| **TCP 53 → 192.0.2.1（TEST-NET，不可路由）** | **同样 0.01s 握手成功** ⇒ 握手是中间盒伪造的 |
| 同上查 A/AAAA | 有时得到 RCODE=REFUSED，有时完全不回 |

结论：本机出口对 `53/tcp` 是「假可达」，是**环境属性**（判据 7 的变体：以前是 RST，现在是 REFUSED/静默），
不是代码 bug。但代码层有两个缺口让它变成每天 8,000 条噪声：

1. **REFUSED 不计入熔断**：`DnsClient.LookupAsync`（`DnsClient.cs:352-367`）只在
   `IsBlockedByPeer(ex)`（`DnsClient.cs:398-429`）返回 true 时调用 `ReportPlainDnsBroken`，
   而该判定只认 `SocketException`（Reset/Aborted/Shutdown）与 `IOException`。
   `ResponseException("…code Refused")` 两个都不匹配 ⇒ `plainDnsBroken` 冷却**从未触发** ⇒ 每轮重试。
2. **空结果只缓存 30s**：同一分支用 `IsSocketException(ex) ? maxTimeToLive : minTimeToLive(30s)`，
   REFUSED 属于后者 ⇒ 30 秒后又来一次。
3. **日志无降噪**：`DnsClient.cs:354` 无条件 `LogWarning`，没有 DohResolver 那种「退避序列首条才 Warn」的处理，
   于是 8,000 条同文案把真正的错误埋掉（10-31 甚至把日志打到 14.5MB/天）。

顺带一个**真实风险**：端口 53 走 `TcpRequestResolver` 时**没有独立超时**
（`resolveTimeout=4s` 只用于非 53 端口的 UDP 解析），
一旦中间盒只伪造握手不回应答，解析会一直挂到上层请求预算耗尽——这正是下面第三节里那些
「正好 25s 的 504」的最后一环。

## 三、真问题：每次重启后 10 分钟的大面积 504

以 v2.6.13 启动（18:19:xx 停机 → 18:20:xx 启动）为例，日志是完整证据链：

```
18:20:0x  DohResolver  DoH 端点 https://223.5.5.5/dns-query 连续失败 4 次，已熔断 2 分钟
18:20:0x  DohResolver  DoH 端点 https://doh.360.cn/dns-query 连续失败 4 次，已熔断 2 分钟
18:20:0x  DohResolver  DoH 端点 https://doh.pub/dns-query 连续失败 4 次，已熔断 2 分钟
18:20:0x  DohResolver  DoH 端点 https://8.8.8.8/dns-query 连续失败 4 次，已熔断 2 分钟
18:20:0x  DohResolver  DoH 端点 https://1.1.1.1/dns-query 连续失败 4 次，已熔断 2 分钟   ← 5 个端点同秒全灭
18:20:xx  DohResolver  DoH 解析 api.github.com 失败：所有端点均不可用，2 秒后重试
18:21:xx  DohResolver  DoH 解析 github.com / collector.github.com / github.githubassets.com 失败：所有端点均不可用
18:21–18:23  25 条 504，耗时整齐地卡在 25001~25333 ms（TaskCanceledException）
18:23–18:24  DoH 恢复，api.github.com/github.com 重新解析成功
18:25 之后   错误归零
```

三个缺陷串联起来才会这样：

1. **重启后候选池是空的**：`dnsendpoints.json` 只持久化 `host:port`
   （`PersistenceService.cs:27` `record EndPointItem(string Host, int Port)`），
   `DomainResolver` 构造时把这些端点一次性塞成 `Array.Empty<IPAddress>()`
   （`DomainResolver.cs:155-159`）——**上次运行验证过的 IP 一个都没留下**。
   于是重启瞬间 22 个域名的候选池全为 0，任何请求都必须走一遍冷解析。
2. **启动批量解析把 5 个 DoH 端点同时熔断**：`TestSpeedAsync` 以 8 路并发
   （`DomainResolver.cs:129`）跑 22 域名 × A/AAAA，而 DoH 是「每域名向全部可用端点竞速」
   且每端点内部还带重试（`QueryEndpointWithRetryAsync`），启动瞬间对每个端点形成十几到几十的并发。
   公共 DoH 会限速/拒绝，而 `endpointFailureThreshold=4`（`DohResolver.cs:93`）是**按次数**计的、
   不区分并发——4 个并发失败在毫秒内凑齐，冷却 `2 分钟`（`DohResolver.cs:105`）立即生效，
   5 个端点在那 1 秒内**一起**进入冷却。
3. **熔断后回落到明文 DNS，而明文 TCP 查询会挂**：见第二节最后一点。
   hosts 源只覆盖部分域名（`api.github.com` 不在 hellogithub 列表里），
   没覆盖的域名此时既没有 DoH 也没有明文结果 ⇒ 请求挂到 `Timeout: 00:00:25` ⇒ 504。

对照 16:42 那次重启（86 次 / 31.7%）与 11-15 之前各天（11-02：13 次全在重启窗口；11-12：10 次全在重启窗口），
**这是长期存在、可稳定复现的结构性缺陷，不是 v2.6.13 引入的回归。**

> 说明：v2.6.13 稳态 0.60% 与 v2.6.12 稳态 0.19% 的差别只有 4 次 vs 1 次，样本量不足，不能判定回归；
> A2 合并策略的健康度可从候选池分布独立验证（见第五节）。

## 五、不是问题的部分（避免误判）

- **候选池健康**：池大小分布 `{0:5, 1:69, 2:303, 3:2092}`，单候选仅 1–3%（`viewscreen` 最高 8%），
  平均 2.8–3.0 个候选 ⇒ v2.6.13 的 A2 合并（上限 8）与 A4 成功 IP 置顶**已生效**，当前不是错误来源。
- **空闲时段无失败**：00:00–14:58 几乎无请求也无 5xx。
- **零散「所有端点不可用」**：全天 121 次中大部分是每小时的 1–6 次抖动，
  集中在空闲时段（用户不可见），真正有影响的是 15:26–15:29（16 次）、20:23–20:26（8 次）这类爆发簇。
- **成功请求耗时**：p50 890ms / p90 4.2s / p99 18.3s（长尾含 49MB Release 下载），
  说明「异常率」之外的核心体验指标是稳的（判据 2）。

## 六、v2.6.14 修复规划

| 级别 | 改动 | 目标指标 |
|---|---|---|
| **P0-1** | `dnsendpoints.json` 扩展为 `{host, port, addresses[], rtt, updatedAt}`；启动直接装载进 `dnsEndPointAddress`，首个请求即用上次验证过的 IP（照常经健康度校验与后台测速淘汰） | 重启后「候选池=0」窗口消失 |
| **P0-2** | 启动预热保护：① DoH 全局并发上限（`SemaphoreSlim(4)`）；② 失败计数去抖——同一端点两次计入失败至少间隔 2s（或并发在途 >1 时不计失败）；③ 预热阶段域名并发 8→2 起步，30s 内逐步放开 | 5 端点同秒熔断不再发生 |
| **P1-1** | 明文 DNS 收口：`ResponseException`（REFUSED/SERVFAIL）纳入「该 DNS 不可用」，连续 3 次进 10 分钟冷却；空结果统一缓存 10 分钟；日志改为「每冷却期首条 Warn、其余 Debug」 | Refused WRN 7,979/日 → <10/日；日志体积 <500KB/日 |
| **P1-2** | 给端口 53 的 TCP 查询套独立超时（复用 `resolveTimeout`，建议 3s），避免挂到请求预算 | 25s 整的 504 消失 |
| **P1-3** | 遥测端点短超时：`collector.github.com`、`api.github.com/_private/browser/*` 用 8s 预算 fail fast | 504 中 66% 的高耗时条目归零 |
| **P2-1** | `Connection: Upgrade` 请求：**已核实无需改动**（同日 60 次 101 成功，升级是通的；400 来自上游对失效会话的应答） | — |
| **P2-2** | 重启后 60s 内抑制自动 IP 刷新，避免与冷启动叠加 | 冷启动压力进一步下降 |

预期（复测口径同第一节表）：重启窗口失败率 31.7%/7.5% → **<2%**；稳态 0.19–0.60% 不劣化；
Refused 日志 7,979 → <10；504 的 p50 从 25.2s 消失（遥测 8s 上限）。自检补充：
`DnsClientSelfTest`（REFUSED 进冷却 / 首条 Warn）、`DohBurstSelfTest`（并发失败不熔断）、
`PersistenceSelfTest`（IP 落盘-装载往返 + 过期 IP 丢弃）。

## 六之二、v2.6.14 实际实施记录（与规划的差异）

| 规划项 | 实际落地 | 差异原因 |
|---|---|---|
| P0-1 IP 持久化 | `dnsendpoints.json` → `{host, port, addresses[{address, elapsedMilliseconds}], savedAtUtc}`；启动装载进 `dnsEndPointAddress` **并**回填 `IPAddressService` 的解析缓存与探测缓存（2 分钟 TTL），旧格式（只有 host/port）仍可读；写入改"临时文件 + 原子替换"，落盘节流 30s | 仅回填地址数组不够：`GetAddressesAsync` 会因"解析缓存已过期"把持久化 IP 丢掉，且不回填探测缓存就要在首个请求路径上重做一次最长 15s 的 TCP 探测 |
| P0-2 ① DoH 全局并发 4 | **未采用**。DoH 的 `requestGate` 是"发起瞬间占闸、立刻释放"，改成全程持有会重犯 v2.6.4 修过的"慢端点堵住快端点"缺陷 | 改在**域名并发**层限流：首轮 3 路，其后 8 路（`COLD_START_CONCURRENCY`） |
| P0-2 ② 失败计数去抖 | 已实现，但**只对"打满超时预算"的失败**去抖（同一端点 2s 内只计 1 次），快失败（连接被拒/TLS 错误）仍逐次计入；另加 3 分钟衰减窗口，避免空闲时段的孤立失败累积成"连续 4 次" | 若对所有失败去抖，真死端点要 4 分钟才熔断，且会让"并发计数不丢"这条既有回归测试失去意义 |
| P1-1 明文 DNS 收口 | `ResponseException(REFUSED/SERVFAIL/NOTIMP)` 纳入不可用（NXDOMAIN 明确排除）；冷却 **10→20→30 分钟递增**，成功查询即清零；日志改为"进入冷却时记一条 Information，其余 Debug" | 单向固定 10 分钟冷却等于每 10 分钟白试一次（两个服务器 288 次/天） |
| P1-2 53/tcp 独立超时 | 4s（A+AAAA 合计），超时抛 `TimeoutException` 并判定"该 DNS 不可用"进入冷却 | 与规划一致；补上"无应答"也要进冷却（本机中间盒会静默丢弃） |
| P1-3 遥测 8s | `TelemetryPolicy`（纯函数 + 自检）：`collector.github.com`/`collector.githubapp.com` 整域 + `/_private/browser/` 路径前缀 → 预算收到 8s，只收紧不放松 | 未把 `github.com/notifications/indicator` 等轮询端点算作遥测：它们是用户可见功能 |
| P2-1 WebSocket | **撤销**。证据见第四节 | 60 次 101 证明升级可用，501 会破坏功能 |
| P2-2 重启后抑制自动刷新 | 未做（v2.6.14 已有 P0-1 让候选池非空，自动刷新的破坏性大幅下降） | 留待实测数据决定 |

新增自检（全部注册进 `--SelfTest`）：`PersistenceSelfTest`（往返/旧格式/坏文件/无效IP/未知域名）、
`DohEndpointSelfTest`（超时回声去抖、快失败不去抖、持续故障仍熔断、衰减、时钟回拨）、
`TelemetryPolicySelfTest`（识别边界与防误杀）。
