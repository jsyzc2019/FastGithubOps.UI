## 先说结论：两个 P1 的原始判断都需要修正

动手前先复核了前提，两条都不完全成立。**这是本次最重要的部分**——
如果照原判断直接改，会引入两处"看起来对但方向错"的改动。

### P1-1「DoH 端点 RTT 在 6 小时内劣化 17 倍，需重估超时预算」

实测（`UseProxy=false` 直连，每个端点 3 次，`github.com` A 记录）：

| 端点 | RTT |
|---|---|
| `223.5.5.5`（阿里） | 443 / 121 / 127 ms |
| `doh.pub`（百度） | 354 / 254 / 127 ms |
| `doh.360.cn`（360） | 186 / 165 / 209 ms |
| `1.1.1.1` / `8.8.8.8` | 三次全 12s 超时（跨境被阻断，与代码无关）|

**当前 RTT 并未劣化**，可用端点仍在 121~443ms，与 v2.6.5 端点列表重建时的实测（148~172ms）同一量级。

所以"重估超时预算"的正确结论是：**固定常数无论调到多少，在网络环境变化后都会失配。**
调小会把慢端点误判为死并触发熔断；调大则让真死端点拖满预算——这是同一个问题的两面，
不可能靠挑一个数同时解决。

### P1-2「`raw.hellogithub.com` 备用 hosts 源持续解析失败，hosts 源更新长期不可用」

日志实测（v2.6.5 全量日志）：

- `已更新在线hosts解析` **9 次**（每次 38~40 个域名）
- `在线hosts源更新失败` **3 次**，失败原因全部是 `不知道这样的主机 (raw.hellogithub.com:443)`

即：**该源在多数时候是可用的**，失败原因是本机明文 53 端口 DNS 被 RST
（与 DoH 端点域名 `doh.pub` 走系统解析失败是同一个根因），属于间歇性失败而非长期不可用。

但排查过程中发现了三个**真实存在**的缺陷 —— 修的是它们，不是原始判断里描述的问题。

## P1-1 修复：超时按端点实测 RTT 自适应

`FastGithub.DomainResolve/DohResolver.cs`

```
超时 = 该端点实测 RTT(EMA) × 3，夹在 [3s, 12s]
```

- **RTT 统计**：只在**成功响应**时采样。超时请求的耗时恒等于超时预算，计入会让 RTT
  单调爬升到上界。
- **EMA 权重 0.3**：网络劣化是渐变过程（长时日志实测 RTT 在小时级尺度上变化一个数量级），
  权重过高会让单次抖动立刻反映到超时上；0.3 既能在约 5 次样本内跟上劣化，又不会被偶发慢包放大。
- **首次访问无样本时退回上界 12s**：不因"还不知道它有多快"而先斩断机会。
- **每次重试单独取预算**：重试的意义就是"再给一次机会"，共享一个 CTS 会让第二次启动时
  剩余预算所剩无几，等于没有重试。
- **上下界必须夹紧**：下界 3s 防止被瞬时快样本压到过短；上界 12s 防止单端点顶穿
  交互域名的 25s 整体预算。

### 修一个自查出来的真实缺陷

`ReportEndpointResult(success: true)` 原本用 `TryRemove` **整条删除**端点状态。
而端点状态同时承担熔断计数与 RTT 统计两个职责 —— 于是每次成功都会把 RTT 历史一起抹掉，
下次超时预算又退回 12s 上界。**自适应等于完全失效，且恰好发生在端点最健康、最该快的时候。**

改为只清熔断字段（`Failures` / `BlockedUntil`）、保留 `RttEma`。
已加断言锁住，避免以后有人又改回 `TryRemove`。

## P1-2 修复：hosts 源可靠性

`FastGithub.DomainResolve/HostsService.cs`、`DomainResolver.cs`

### 1. 失败后无节流（与刚修的 P0 同源）

`RefreshAsync` 有 4 个调用方：后台 1 小时定时、健康度触发的 `DomainResolver.RefreshAsync`、
UI 的 hosts-only 刷新、以及 IP 拉黑后的恢复刷新。恢复路径只有**每域名 10 秒**冷却，
**没有全局节流** —— 多个域名同时被拉黑时会并发进入，多个拉取同时打向同一个源。

- 成功节流：5 分钟内不重复拉取（内容等价，无收益）
- 失败退避：5min → 10min → 20min …，封顶 2h。
  实测失败原因是本机 DNS 解析不出该域名，这类失败**不会自行好转**，密集重试毫无意义
- 合流：`SemaphoreSlim(1,1)`，并发进入者等待首个结果而非各自发一次

### 2. `HttpClient` 未禁用系统代理

原实现走默认代理设置。本机若配置了代理环境变量，"源不可达"可能只是代理拒绝 ——
而 DoH 通道是 `UseProxy=false` 直连，**同一个域名两个通道结论互相矛盾**，
正是"探针语义必须与被测组件一致"的典型陷阱。已统一为 `UseProxy=false`。

### 3. 空响应会清空映射

原实现无条件先 `Clear()` 再逐条填入。源一旦返回空文件或被劫持成空内容，
已有映射立即消失，程序要等下次成功拉取才能恢复。改为**仅在解析出非空映射时才替换**，
失败时保留旧映射，并在日志中说明"保留上次成功拉取的 N 个域名" ——
静默沿用会让人误以为源是好的。

### 4. 停机被计入失败

补 `catch (OperationCanceledException) when (cancellationToken.IsCancellationRequested)`，
整体停机不计失败、不告警。

### 手动刷新绕过节流

UI 的「手动刷新」是用户显式动作，语义上必须"现在就去拉"，因此新增 `force` 参数。
否则用户点了没反应，会被当成程序卡死 —— 节流把优化做成了故障。

## 自测

新增 8 项断言（P1-1 共 6 项 + P1-2 间接），全部通过：

- 无 RTT 样本时退到上界 12s
- RTT 150ms 的快端点被夹到下界 3s
- RTT 劣化后预算跟着变大
- 劣化后不超过上界 12s
- **慢端点劣化不牵连快端点**（各自独立预算，这正是自适应相对"调大固定值"的核心价值）
- 极端 RTT 上下界都夹紧
- **成功上报后 RTT 历史未被清掉**
- 成功上报后熔断计数确实清零（确认上一个修复没让原职责失效）

编译 **0 警告 0 错误**，`IpAddressFilter 36 项 + DohBackoff 38 项` 全部通过。
