# v2.6.4

> 目标：把 v2.6.3 实测残留的三个问题一次性收口 —— 冷启动残余 504、退出不干净、DNS 污染反复出现。

## 一、DoH 多端点并发竞速（消除冷启动残余 504）

### 问题

v2.6.3 仍有 6 个 504，全部集中在启动后 33 秒内。日志时序显示：

```
22:01:51  请求发起（github.com、api.github.com）
22:02:16  504（耗时 25.4s / 25.0s，TaskCanceledException）
22:02:21  github.com 解析成功  ← 整整 30 秒
```

30 秒的构成完全来自 `DohResolver` 的"国内优先 + 命中即止"**串行遍历**：
一个端点失败要等满 `perRequestTimeout(12s) × 重试(2)` 才轮到下一个，
冷启动时三个端点各等一轮 = 最坏 72 秒。

关键在于：**串行遍历假设"排在前面的端点更快"，但冷启动时这个前提不成立**
（TLS 握手要现建、端点侧可能正在排队）。

### 修法

同时向所有**未被熔断**的端点发起查询，用 `Task.WhenAny` 收割首个返回者，
成功后立即取消其余在途请求。

### 为什么并发是对的（不是退化的暴力方案）

所有标准 DoH 服务器对**同一域名、同一记录类型**返回同一份权威答案（都来自权威 NS），
只是延迟不同。所以"最快端点的答案"与"逐个尝试的答案"**内容完全一致**，
但耗时从"最慢端点的累加"降到"最快端点的 RTT"。

按本机实测可达端点 RTT（100~240ms），单域名首查应从 30 秒降到**亚秒级**，
远低于交互域名的 25 秒预算。

### 流量代价可控

- 熔断机制继续生效：连续失败的端点 10 分钟内不再参与，跨境死端点很快退出竞速。
- 首个成功后立即 `winnerCts.Cancel()`，其余请求当场作废，正常不会打满 4 个。
- 新增**全局在途请求闸门 `SemaphoreSlim(8)`**：竞速把"单域名 4 并发"叠乘到
  "冷启动同时解析十几个域名"，峰值可达 120 并发 HTTPS，形态过于像攻击流量。
  闸门把它压到 8 —— 8 路远高于端点 RTT，不构成瓶颈。
- 综合下来总请求数与总耗时都是**净减少**（不再是"每个域名串行各等 12~24s"）。

## 二、退出链路修复（关闭不留后患）

### 1. `ShutdownTimeout` 从 1 天改为 5 秒

原值 `TimeSpan.FromSeconds(1d)`。停机时 Host 会为每个在途请求最多等 1 天才放弃，
导致"关闭应用"后主进程迟迟不退出、端口不释放、WinDivert 持续拦截。
用户观感是"关了还在生效，重开又报端口占用"。

### 2. UI 退出显式通知主程序（新增 `/shutdown` 端点）

原来 UI 关闭只 Dispose 自己的托盘图标，主程序**完全不知情**，
只能靠 `WaitForParentProcessExitAsync` 轮询父进程。
UI 被任务管理器强杀或自身崩溃时这条链路不可靠，
主程序变成孤儿进程 —— **WinDivert 仍在拦截流量**，用户以为已关闭、实际未关。

现在：
- 主程序新增 `/shutdown` 端点（只监听在 localhost 内部端口，不对外暴露），
  先回响应、再异步 `StopApplication()`，避免客户端被自己的停机动作卡住。
- UI 的「关闭应用」改为：确认 → 通知 `/shutdown` → 关自己。
- 父进程轮询保留为兜底。

### 3. 「点 X」的语义明确化

原 `WndProc` 把 `SC_MINIMIZE` 和 `SC_CLOSE` 一律改成 `Hide()`，
于是"点 X"和"点最小化"效果完全相同，且**没有任何提示** ——
用户极易误以为应用已关闭，实际主程序还在拦截网络。

现在：
- 最小化：静默隐藏。
- 点 X：隐藏到托盘 + 气泡提示"已隐藏到托盘，GitHub 仍在加速。要退出请右键托盘图标并选择「关闭应用」"。
- 真正的退出入口统一为托盘菜单「关闭应用」，且**带确认对话框**
  （关闭后 GitHub 立刻回到直连，误点一次用户会明显感觉"怎么又变慢了"）。

### 4. 父进程退出不再记成 Error

原 `WaitForParentProcessExitAsync` 用 `WaitForExit()` 无限阻塞且无日志，
异常一律 `LogError`（"查父进程失败"多是权限或进程已消失等正常情况）。
现在改为 500ms 轮询 + 明确日志；`ArgumentException`（进程已不存在）按"已退出"处理，
其余异常降为 `Warning` 而非 `Error`。

## 三、DNS 污染改用网段归属过滤

### 为什么不能继续拉黑 IP

逐个 IP 拉黑**永远无法收敛**：污染源返回的地址每次都不同。
日志里同一个 `github.global.ssl.fastly.net` 先后返回过
`173.252.108.21` → `151.101.53.194` → `199.232.17.194`。
黑名单挡得住手头这几个，下一轮换个就又漏进来（v2.6.3 就是这样，
污染地址进了候选池，靠下游 TCP+TLS 探测才淘汰，白花建连与重解析成本）。

### 修法

GitHub 及其 CDN（Fastly、Azure）的边缘节点只可能落在若干**固定的、公开的**网段内。
反过来，有些整段地址**明确属于境外社交/广告网络**，是 GFW DNS 污染惯用的伪造应答源，
物理上不可能是 GitHub 边缘节点 —— 按整段拒绝即可，收敛且不会误杀。

已收录（取自各机构公开地址分配表）：
- Meta/Facebook（AS32934）：`173.252.0.0/16`、`31.13.0.0/16`、`31.6.0.0/15`、
  `157.240.0.0/16`、`179.60.192.0/22`、`185.60.216.0/22`、`102.132.96.0/20`、`163.70.128.0/17`
- Meta IPv6：`2a03:2880::/32` —— 污染应答常带 `face:b00c` 签名（Facebook 标志），等于自带身份声明

**刻意不拦** `2606:4700::/32`（Cloudflare）—— Fastly 边缘节点就在其中。

### 配套自检（关键）

新增 `IpAddressFilterSelfTest`，36 项断言，覆盖两类：
- **必须拒**：实测污染地址（含 `173.252.108.21`、`2a03:2880:...:face:b00c:...`）与各保留段
- **必须放行**：v2.6.3 实测日志中 GitHub/Fastly/Azure 的**全部真实边缘 IP**
  （`20.205.243.166`、`140.82.121.5`、`185.199.109.133`、`151.101.53.194`、
  `199.232.17.194`、`4.225.11.194`、`2606:4700::1` 等）

这个自检当场抓出过一个真 bug：`MatchPrefix` 原本要求地址与网段**长度严格相等**
（为 IPv4 的 4 字节设计），导致 IPv6 传 4 字节前缀时 `16 != 4` 直接返回 false ——
**Meta IPv6 段静默失效，肉眼完全看不出来**。已改为允许前缀短于地址。

## 实测要看什么

1. **冷启动前 30 秒的 504 是否归零**（v2.6.3 是 6 个，v2.6.2 是 18 个）。
   日志里 `DoH 解析 github.com 成功` 与首条 504 的时间差应从 30 秒降到亚秒级。
2. DoH 端点并发是否造成异常 —— 应能看到"很快就有端点返回"，而不是一路等 12 秒。
3. 解析结果里是否还出现 `173.252.x.x` / `31.13.x.x` / `2a03:2880:...`（应完全消失）。
4. 托盘「关闭应用」→ 确认 → 主程序是否**干净退出**（端口释放、进程消失）。
5. 关闭后重新启动，是否还会报端口占用。

## 已知遗留

- `4.225.11.194` 曾混入 `github.com` 的解析结果。该地址归属 Microsoft Azure，
  **是合法公网地址**（不是污染），故不在过滤范围内。若要更严格，只能做
  "IP 归属 + TLS 握手结果"联合判定，属更大改动。
- 完整白名单式过滤（只放行 GitHub/Fastly/Azure 已知段）会更严格，
  但会牺牲对新 CDN 节点的兼容性，需谨慎评估。
