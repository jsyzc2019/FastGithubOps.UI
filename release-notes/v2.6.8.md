# v2.6.8

修复 v2.6.7 实测日志暴露的三个缺陷，其中两个构成互锁故障链 —— 它们共同导致用户看到的
`找不到任何可成功连接的IP ...（已尝试 0 个候选IP）`。

## P0-1 建连总预算与单候选预算矛盾，候选 2、3 永远试不到

`appsettings.github.json` 里 `github.com.ConnectTimeout = 12s`，而代码里
`totalConnectBudget = 10s` —— **总预算比单个候选的预算还小**。

第一个候选的 linkedToken 上同时挂着 12s 与 10s 两个令牌，10s 那个先到，于是直接
`break`。也就是说 `MAX_TRY_COUNT = 3` 对 github.com 实际是死代码：候选 2、3 一次都没试过。

更糟的是报错文案。该分支取 `innerExceptions.Count` 作为"已尝试候选数"，而此刻还没往
`innerExceptions` 里 Add 过任何异常，**计数恒为 0**：

```
System.TimeoutException: 在 10s 内未能连接 github.com（已尝试 0 个候选IP）
```

这条消息把"第一个候选吃光了预算"误报成"解析层一个 IP 都没给出"，会把排障方向带偏。
实测日志中 4 条用户可见的 502 全部是这同一个原因。

修复：

- 单候选预算 = `min(ConnectBudget, 剩余总预算 / 剩余候选数)`。
  三个候选共享 10s，各约 3.3s；而 github.com 单 IP 的健康耗时实测仅 0.4~1.1s，
  3.3s 足够完成 TCP+TLS，因此三个候选都能真正参与竞争。
  只有 1 个候选时它独享全部 10s（等价于原行为）。
- 报错文案改用真实尝试次数，并打印 `已尝试 n/候选总数`。

## P0-2 DoH 熔断死循环 —— 熔断从未真正让端点休息过

v2.6.7 的熔断日志时刻精确地每 10 分钟一轮：

```
15:59:23 → 16:10:25 → 16:20:35 → 16:31:14 → 16:41:37 → 16:51:50
```

5 个 DoH 端点在启动后 25 秒内全部熔断，此后一小时内 DoH 成功 63 次、失败 97 次 ——
熔断几乎没带来收益。

机制是三件事叠加：

1. 阈值只有 2 次，任何端点只要抖动两次就被判死；
2. 冷却固定 10 分钟；
3. 失败退避上限 60 秒 —— 20 个域名的退避在 10 分钟冷却里**早就全部到期**。

于是冷却一过，积压的 20 域名 × A/AAAA = 40 个查询在同一瞬间全部打向 5 个端点
（**200 并发**），端点排队限速 → 又连续失败 2 次 → 立刻二次熔断 10 分钟。
恢复窗口**必然**被积压洪峰填满 —— 这是结构性的，不是偶发。

修复：

- 熔断阈值 2 → 4：单次网络抖动不再触发熔断。
- 冷却改为递增：2 → 4 → 8 → 16 → 30 分钟封顶。偶发抖动只短暂休息；
  真正不可达的端点（跨境 1.1.1.1 / 8.8.8.8）会逐次加长，最终稳定在 30 分钟。
- 新增标准的**半开三态**（冷却 → 半开 → 关闭）：冷却到期后只放行**一个**试探请求，
  其余调用方跳过并等待它的结果。端点真恢复时，1 个请求（百毫秒级）即可确认，
  代价从"40 请求的并发洪峰"降到 1 个；若试探失败则按递增冷却重新熔断。
  这正是打断死循环的关键一环。

## P1 大附件上传被本地 30 秒超时砍断（此前误判为 GitHub 限制）

v2.6.7 曾把 53MB 附件切成 8 卷上传，理由是"GitHub 附件上传有 30 秒硬上限"。
审计实测日志后确认这个判断是错的：

```
POST https://uploads.github.com/... responded 504 in 30010.7913 ms
POST https://uploads.github.com/... responded 504 in 30061.3561 ms
...共 11 个
```

**所有 504 的耗时全部落在 30010~30061ms，也就是精确的 30.000 秒。**
这是 `appsettings.github.json` 里 `*.github.com` 的 `Timeout = 00:00:30`
掐断后由 YARP 映射成 504，与 GitHub 服务端无关。

同一时段那 8 个 6.6MB 分卷里有 6 个成功（9.6~14 秒），说明链路本身完全健康，
只是单个大文件超过了 30 秒预算。

修复：

- `uploads.github.com` 精确条目：`Timeout = 00:20:00`、`ConnectTimeout = 00:00:20`。
- `release-assets.githubusercontent.com`：`Timeout = 00:10:00`。
- 已验证 `DomainPattern` 的排序规则中 3 段精确条目优先于 2 段通配条目
  （排序索引 5 vs 7），因此精确配置确实能优先命中。

**结论：53MB 附件可以一次性上传，无需分卷。**
