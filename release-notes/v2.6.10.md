# FastGithubOps.UI v2.6.10

> 仅 win-x64。解压后运行 `FastGithub.UI.exe`，首次使用请以管理员身份运行以自动导入 CA 证书。

## 本版针对 v2.6.9 实测日志（log20261007）的两处修复

v2.6.9 发布后实测反馈"体验感有所下降"。审计 `publish/v269/logs/log20261007.txt`
（5.6 小时 / 2376 请求）后确认：**异常率升到 12.25%**（264×502 + 26×504），
但根因**不是 v2.6.9 新增的代码缺陷**，而是一个 v2.6.9 方向的过头修正，
叠加一个 v2.6.8 就存在、从未被发现的机制失效。

### 先说清"卡"在哪里（否则会误判方向）

按时间聚集性分析，**99%（287/290）的错误集中在 14:04–14:29 这 25 分钟内**，
其余5 小时几乎全干净（camo 图片请求在故障窗口内失败率 28.6%，窗口外 **0%**）。
这符合"上游波动会自愈"的特征，属于外部网络波动，而非本地缺陷的均匀劣化。

而用户感知的"卡"主要不来自失败，而是来自**成功请求的耗时**：

| 指标 | v2.6.9 实测 |
|---|---|
| 成功请求 p50 | 837ms |
| 成功请求 p90 | **18.9s** |
| 成功请求 p99 | **67s** |
| camo（图片）200 响应 p50 | **10.8s** |
| camo p90 | **46.5s** |
| camo >10s 占比 | 51.2% |

另需注意：502 的耗时 p50 = **0.8ms**，61.4% 在 10ms 以内 ——
亚毫秒失败是**本地快速拒绝/客户端取消**，绝不是网络丢包。
所以 502 数量大≠ 链路严重劣化，页面元素缺失（图片挂）才是它的实际表现。

### 修复一：单IP 候选的拉黑时长10s → 30s（v2.6.9 的过头修正）

v2.6.9 把池=1 的拉黑时长从 30s 压到 10s，目的是缩小"单 IP 域名被拉黑＝整域名
瞬时不可用"的窗口。但方向过头了：

`camo.githubusercontent.com` 的建连 p50=10.8s / p90=46.5s，
属"**建连本身就慢**"的域名。**10s 拉黑窗短于一次正常握手**，
于是该IP 被拉黑 10s → 刚过冷却期立刻又被判定失败 → 反复拉黑，
实际处于"永远在抖动"的状态。

同时实测"在 10s 内未能连接"（总预算耗尽）**141 次**，
其中"已尝试 1/3 个候选" 29 次、"1/2" 17 次——
池子明明有多个候选，却在第 1 个候选耗尽总预算后直接 break，
候选 2、3 根本没被试。

**改动**：池=1 的拉黑时长回到 30s（与池≥2 对齐）。
差异化的保护仍由失败次数阈值承担（池=1 需 4 次、池≥2 需 2 次），
兜底仍是"全部拉黑时强制回退重试"，因此不会退化为"恢复慢"。

### 修复二：DoH 递增冷却对"抖动型端点"永久失效（v2.6.8 遗留，从未被发现）

v2.6.8 引入了半开三态+ 递增冷却（2→4→8→16→30 封顶）以打断熔断死循环。
但v2.6.9 实测日志显示 `223.5.5.5/dns-query` 从 14:12 到 19:10
**反复熔断 40+ 次，每次都是"已熔断 2 分钟"** —— 递增从未生效。

**根因**：`ReportEndpointResult` 的成功分支里有 `ConsecutiveBlocks = 0`。
该端点属"半可用"（故障窗口内 DoH 整体成功率 52.8%），
会在两次失败之间成功一次 —— **每次成功都把递增计数清零**，
于是 `ComputeCooldown(++ConsecutiveBlocks)` 永远取第 1 档。
熔断机制在抖动场景下退化成「熔断 2 分钟 → 放行 → 再熔断 2 分钟」的无限抖动，
恰是这个机制本该消除的行为。

**改动**：只有**半开探测成功**才清零递增计数。
普通轮次命中（端点本来就在正常服务、只是这次恰好成功）不清零——
它的成功不构成"恢复"的证据，真正的恢复必须由"冷却到期后放行的那一个试探请求"证明。

### 自检：补上"函数对、调用路径断"这类缺陷的覆盖

既有 `TestCooldownEscalates` 只测`ComputeCooldown` 这个**纯函数**本身正确，
无法发现"调用路径把参数清零"这类缺陷 —— 而真实故障恰恰是后者。
本次新增两条集成断言：

- `TestCooldownEscalatesOnFlappingEndpoint`：复现"失败→冷却到期→普通成功→再失败"模式，
  断言每轮熔断时长**逐次拉长**。
- `TestHalfOpenSuccessResetsEscalation`：断言**半开成功才清零**，
  防止矫枉过正（真正恢复的端点不该永远背着递增惩罚被跳过）。

同时修订 `TestSingleCandidateBlacklistShorter`：
原用例断言"池=1 拉黑时长应短于多候选"，与本次修复方向相反，
现改为断言"拉黑窗 ≥ 慢建连耗时（20s 下限）"这一硬约束。

## 通用教训

1. **"把惩罚调小以加快恢复"必须验证惩罚窗与真实失败耗时是否同量级。**
   压到比一次正常握手还短时，机制就从"惩罚坏节点"变成"惩罚正常节点"。
2. **自检只测纯函数不够**：必须有一条覆盖"谁调用它、参数有没有被改掉"的集成断言。
   函数正确 + 调用路径断掉 = 缺陷照样发生（本例即`ConsecutiveBlocks` 被成功分支清零）。
3. **递增惩罚的计数不能在"任意一次成功"时清零**，否则对间歇性可用节点永久失效。
   真正的恢复证据只能来自"冷却到期后的那一次试探"。
4. **异常率不等于体验**：亚毫秒快速失败会被计入异常率但不产生等待感；
   而 p50 10.8s 的"成功"请求才是页面卡顿的主因。**审计必须同时看错误率和成功耗时分布。**
5. **判"本地缺陷 vs 上游波动"仍以时间聚集性为准**：缺陷全程均匀劣化，上游波动会自愈。
   本次 99% 错误挤在 25 分钟内 → 上游波动；其余 5 小时干净。
